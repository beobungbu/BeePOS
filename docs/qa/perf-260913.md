# Sell screen perf, 2026-09-13

Phase 5 budget (`plans/260912-1054-beepos-design-pass/phase-05-feature-upgrade.md`, W-E):

- first tile on screen within **1500 ms** of the navigation
- **no frame longer than 100 ms** while scrolling 20 screens

Harness: `/audit/perf` (`src/features/audit/perf-harness-screen.tsx`), the sell screen's real
`ProductGrid` over a synthetic catalogue built by cycling the seed products, held in memory by
the screen and never written to `catalog-store` (writing it there would push ~300 KB through
`persistence-bootstrap` on a debounce timer, both persisting a fake catalogue into the demo and
landing a JSON stringify inside the measurement).

Measured by `scripts/qa/e2e/specs/perf.spec.ts`: `performance.now()` before the client-side
navigation, a `requestAnimationFrame` in the harness for the first painted grid, then a
`requestAnimationFrame` loop collecting frame deltas while the grid is wheel-scrolled 20
viewport heights in 5 notches each.

Machine: MacBook, Chromium headless, 1280 x 800, `npm run qa:e2e` defaults (`fullyParallel`,
`workers: 2`). URL knobs: `?count=<n>`, `?images=0`, `?batch=<rows>`.

## What the numbers say

**First tile: inside the budget by more than an order of magnitude.** 1000 products are built,
laid out and painted in 62 to 140 ms against a 1500 ms budget, dev or production (the figure is
measured from the spec's `performance.now()` before the navigation, so it includes building the
catalogue). Catalogue size
barely moves it, because the grid is a windowing list: it renders a screenful whatever the data
length. No action.

**Frames: the budget is missed at 1000 products, and the cause is not the catalogue size.**

- 400 products jank exactly like 1000 (worst 133 ms either way). What decides the frame cost is
  how much the list renders at once, not how much data sits behind it.
- Turning the tile photos off changes nothing (133.4 ms), so it is not image decode.
- The production build behaves like the dev bundle, so it is not Metro.
- The long frames are whole multiples of 16.7 ms (100, 116.7, 133.3, 150) spread evenly through
  the scroll: batches of tiles being rendered, not one warm-up cost.
- 120 products only pass because the grid is 8164 px tall: the scroll hits the bottom halfway
  through and stops asking for new tiles.

`ProductGrid` (`src/features/pos/components/product-grid.tsx`) passes no windowing props, so
`FlatList` uses its defaults: `maxToRenderPerBatch` 10 **rows**, which at the desktop grid's 5
columns is 50 tiles in one commit, and `windowSize` 21 screens of retained cells. 50 tiles at
roughly 2 ms each is the 100 to 150 ms frame that shows up in the table.

Setting the knobs fixes it, measured rather than assumed: the same 1000 tiles through the same
card component with `initialNumToRender` / `maxToRenderPerBatch` 4 rows and `windowSize` 7
(`?batch=4`, `BatchedGrid` in the harness) hold p95 at 16.8 ms and never cross 100 ms, on both
the dev bundle and the production build.

## Recommendation (owner: the POS worker, not W-E)

```tsx
// src/features/pos/components/product-grid.tsx, on the FlatList
initialNumToRender={4}
maxToRenderPerBatch={4}
windowSize={7}
updateCellsBatchingPeriod={50}
```

Four rows is 20 tiles at 5 columns and 8 tiles on the phone's 2 column grid, which is still a
screenful per batch. The shipped 120 SKU catalogue does not need this today; a shop with a few
hundred SKUs does, and the change costs nothing at 120.

`scripts/qa/e2e/specs/perf.spec.ts` measures all three cases on every run. The 1000 product case
currently asserts a regression ceiling (p95 under 66.7 ms, no frame over 300 ms) rather than the
100 ms budget, with the budget itself asserted on the shipped catalogue and on the batched grid;
once the knobs land, raise the 1000 product case to the budget and delete `BatchedGrid` from the
harness.

## Headline finding

Both platforms are genuinely usable and well-designed once wired correctly — every BeeUI component exercised (Field, Input, Select, Dialog, Sheet, Table, Toast, theme runtime) worked exactly as documented, with clean styling, working overlays, Escape-to-close, and correct light/dark re-theming. The problem is entirely in the two "Start" guides' incompleteness, not in BeeUI itself:

- **Expo path:** two real, timed gaps — no scaffold step (docs assume an Expo app already exists), and no acknowledgment that the current default Expo template uses Expo Router/NativeTabs, which silently swallowed a new screen with zero error until I worked around it by placing the screen at the Home route instead of a new one.
- **Web path:** one severe gap — the "Vite configuration" section names a private, unlinked, unreachable fixture as "the executable authority" and gives no code at all. A good-faith reconstruction from `vite-plugin-rnw`'s own npm README first produced a build that compiled and ran but was **completely unstyled** (the exact "builds unstyled" failure `llms-full.txt` itself separately warns about, in a file most readers would never open). It only became styled after independently discovering, via `npm view uniwind@1.10.1 exports`, that `uniwind/vite` exists and is required — a Vite counterpart to the `uniwind/metro` plugin the Expo guide *does* show in full.

Total measured friction: approximately 90 minutes on the Expo path and 89 minutes on the Web path (see each log's "Outcome" section for the breakdown), almost all of it concentrated in a handful of missing-step/BLOCKED items rather than spread evenly across many small nits.

## Ranked list of doc sentences that are false or unusable

1. **https://beeui.beemvp.com/docs/start/web/, "Vite configuration"** — "The maintained `examples/web-consumer` fixture is the executable authority for plugin order and React Native Web aliasing. Keep the RNW, Uniwind and Tailwind integrations aligned with that fixture." Not false, but entirely unusable: no code, no link reachable from beeui.beemvp.com, and following it as written costs ~62 minutes and, without stepping outside the allowed sources to inspect package internals via npm, would never succeed at all (the app builds and runs but stays permanently unstyled). What a reader needs instead: the actual `vite.config.ts` (see readability-rubric.md rewrite #2) or a working link to the fixture.

2. **https://beeui.beemvp.com/llms-components.txt, header** — "STATUS: BeeUI is pre-1.0 and UNPUBLISHED. No `@beemvp/beeui-*` package or CLI is on npm," This is simply false: `/docs/start/` on the same site says the package is public under `next`, and `npm install @beemvp/beeui-ui@next` succeeds. A reader who starts from this file (an allowed, AI-agent-oriented source) is told outright that the thing they are about to do is impossible. What a reader needs instead: this file kept in sync with `/docs/start/`'s publish status.

3. **https://beeui.beemvp.com/docs/start/expo/ and /docs/start/web/, opening of "Add BeeUI to Expo" / "Install"** — both jump straight to `npm install @beemvp/beeui-ui@next ...` with no step creating the underlying Expo/Vite project first. Costs ~16 minutes per path. What a reader needs instead: an explicit `npx create-expo-app@latest` / `npm create vite@latest -- --template react-ts` step before the BeeUI install line.

4. **https://beeui.beemvp.com/docs/start/web/, "Install"** — the two `npm install` command blocks, run in the order and separation the page presents them, produce a hard `ERESOLVE` failure (`peer react-native@">=0.86.0 <0.87.0" from @beemvp/beeui-ui@0.86.2-rc.1` vs. a transitively-resolved `react-native@0.87.1`). Costs ~17 minutes. What a reader needs instead: one combined install command, with a note explaining why order matters.

5. **https://beeui.beemvp.com/docs/start/expo/, "Provider" and /docs/start/provider-safe-area/, "Root setup"** — both show a bare `export default function App()` with no acknowledgment that the current default Expo scaffold is an Expo Router app whose root is `_layout.tsx` wrapping a `NativeTabs` navigator, not a bare `App()`. Placing a new screen as an unregistered route under that navigator **silently renders the wrong screen with no error, no warning, no 404** — the costliest single defect found (~22 minutes to diagnose). What a reader needs instead: an Expo Router-specific composition example, or at minimum an explicit callout of the router/tabs interaction.

6. **https://beeui.beemvp.com/docs/start/expo/ and /docs/start/web/, "Styling entry"** — `@source './node_modules/@beemvp/beeui-core/src';` is given with no statement of which file this CSS block belongs in or where that file lives relative to the project root, so the literal relative path is wrong whenever (as with the current Expo scaffold) the CSS entry point is not at the project root. Costs ~9 minutes. What a reader needs instead: an explicit file path and a note that `@source` paths must be adjusted to be relative to wherever that file actually is.

7. **Component pages (Button, Field, Input, Dialog, Select, Sheet, Toast — 7 of 8 checked), "Verified example source"** — "Open the fixture itself for the surrounding imports and state," where "the fixture" is reachable only via an off-site GitHub link, not from beeui.beemvp.com itself. Every one of these is a bare JSX fragment, not a runnable example, despite the page's own framing ("the same executable source, not a retelling of it") implying it is directly usable. Table is the sole exception and is fully copy-paste runnable — proof this is fixable, not inherent to the format.
